# Process mining для 1С: где процесс ждёт и возвращается назад

[![CI](https://github.com/sergey-lastochkin/process-mining-1c/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/sergey-lastochkin/process-mining-1c/actions/workflows/ci.yml)

**Анализ журналов бизнес-событий: самые частые варианты процесса, узкие места
(ожидания между шагами) и возвраты на доработку.** Плюс готовый формат
выгрузки событий из 1С, без которого такой анализ не сделать.

![Частые варианты и длинные ожидания](studies/bpi-challenge-2012-2026-08-10/graphs/variants-bottlenecks.svg)

## Какую проблему решает

Руководитель видит, что заявки «долго согласуются», но не знает, на каком шаге и
почему. Журнал регистрации 1С для этого почти бесполезен: в нём технические
события, а не бизнес-шаги. Проект даёт две вещи:

1. [Контракт бизнес-события](onec_export/event-contract.md) — какие поля
   выгружать из 1С (`case_id`, действие, состояние до/после, роль, причина), чтобы
   процесс можно было восстановить, не выгружая персональные данные.
2. Код, который по такому журналу считает варианты, ожидания p50/p90/p95 между
   шагами, возвраты и эвристических кандидатов на автоматизацию.

## Для кого

- Компании на 1С, которые хотят найти, где теряется время в согласовании заявок,
  заказов или платежей, до того как заказывать доработку.
- Аналитики, которым нужен воспроизводимый расчёт вместо ручной выборки.

## Запуск за 2 минуты

```bash
git clone https://github.com/sergey-lastochkin/process-mining-1c.git
cd process-mining-1c
python3.12 -m venv .venv
.venv/bin/python -m pip install -e '.[dev]'
PYTHONPATH=src .venv/bin/python -m pytest -q
PYTHONPATH=src .venv/bin/uvicorn process_mining.api:app   # http://127.0.0.1:8000/docs
```

API принимает события через `POST /events` и отдаёт варианты, ожидания,
кандидатов и DOT-граф. Прогон на полном открытом журнале — в
[runbook](docs/runbook.md).

## Пример результата

Проверка на полном открытом журнале BPI Challenge 2012 (заявки на кредит в
нидерландском банке): 262 200 событий, 13 087 случаев, 24 действия, 4 366
вариантов. Полный анализ — 10,2 с.

- Самый частый вариант (26 % случаев): `A_SUBMITTED → A_PARTLYSUBMITTED → A_DECLINED`.
- У 9 658 из 13 087 случаев есть повторные действия (возвраты).
- Самое долгое ожидание среди частых переходов (≥100 раз):
  `W_Completeren aanvraag → W_Nabellen offertes`, p95 — 8,2 суток.

## Ограничения

- **Данных 1С в проекте нет.** Алгоритмы проверены на открытом банковском журнале;
  для 1С есть только контракт выгрузки, сама выгрузка пишется под конкретную базу.
- Самый частый вариант — статистическая точка сравнения, а не утверждённая схема
  процесса.
- Оценка кандидатов на автоматизацию эвристическая и не заменяет расчёт эффекта.
- API хранит события в памяти — это не хранилище журналов компании.
- Сырые данные BPI не распространяются; перед скачиванием проверьте условия 4TU.
